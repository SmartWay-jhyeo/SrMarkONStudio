# 젯슨 링크(J29)에 Cloud 스키마 싣기 — A단계 설계

2026-08-21. 사용자 결정: "cloud로 보낼 때 바로바로 보낼 수 있으니까 이 규약을
따르는 게 좋겠어."

## 1. 배경과 목적

전작(차선 관제 시스템 Q2)의 Edge→Cloud 파이프라인이 젯슨에 이미 있다
(`~/Smartway/SrLaneControlSystem_Embedded_Jetson_Lanemark` — UART NDJSON 수신
→ MQTT publish). 그 파이프라인이 먹는 페이로드 계약이
**`docs/데이터 스키마 명세서_v1.6.0.md`** 다.

MarkON 보드가 J29(USART2) 링크로 **그 계약을 그대로 말하면**, 젯슨 소프트웨어
수정 없이 센서 데이터가 Cloud 까지 직행한다. 지금 J29 로 나가는 것은 규격 v3
텔레메트리의 바이트 미러인데(2026-08-21 결선 검증용), 이것을 **Cloud 스키마
직렬화기로 교체**한다.

🔴 **실측 확인 (2026-08-21)**: 젯슨 앱 `_lanemark_serial.py` 는 `$` 로 시작하지
않는 줄을 통째로 `json.loads` 한다 — 체크섬·프레이밍 없음. Cloud 스키마 JSON
한 줄 + `\n` 이면 그대로 통과한다. 기대 baud 는 2M 이지만
`LANEMARK_SERIAL_BAUD` 환경변수로 젯슨 쪽에서 921600 에 맞출 수 있다.

## 3. 구조

```
                    ┌─ mk_telem ──(규격 v3 NDJSON)──▶ mk_uart(USART3) ─▶ PC GUI
 수집원 (공유)  ────┤
 MkAds·MkI2c·      └─ mk_cloud ──(Cloud 스키마 v1.6.0)─▶ mk_jet(USART2) ─▶ 젯슨 ─▶ MQTT ─▶ Cloud
 MkSolCtl·MkGnss
```

- **`app/mk_cloud.c` 신설** (HAL 비의존 — 호스트에서 시험). mk_telem 과 같은
  수집원을 읽는 **병렬 소비자**다. mk_telem 은 한 글자도 안 바뀐다.
- **`bsp/mk_jet.c`**: `main.c` 의 `emit_telem()` 에서 미러 호출을 제거하고,
  mk_cloud 의 emit 콜백을 `mk_jet_write()` 에 배선한다. 링·DMA·핀은 그대로.
- 슈퍼루프가 `mk_cloud_tick(&cloud, now, emit, NULL)` 을 부른다
  (mk_telem_tick 과 같은 자리·같은 계약 — 줄을 만들어 링에 넣고 즉시 반환).

## 4. 레코드 매핑

### 4.1 공통 필드 (계약 §1)

| 계약 필드 | 값 | 출처 |

| `schema_ver` | **1** 고정 | 계약 §15 (Q1·Q2 = 1) |
| `device_id` | `"1"` | 기존 `DEVICE_ID`(main.c) — 계약의 "정수 문자열" 관례와 일치 |
| `t` | int64 UTC epoch ms | `acquired_epoch_ms()` 와 같은 변환 (획득 시각, 설계 원칙 2) |
| `type` | 아래 표 | 설정에서 결정 |
| `time_source` | 아래 매핑 | `mk_timeax_grade()` |

**time_source 매핑** (계약 §1 ↔ 규격 v3 §7.1.2):

| MarkON 등급 | 계약 값 |
|---|---|
| `gnss_pps` | `"gnss"` |
| `gnss_nmea` | `"gnss_nmea"` |
| `device_clock` | `"device_clock"` |

### 4.2 아날로그 (ain) → 분사압·유량

채널 설정 `ain{n}.cloud`(열거, 신규 — §5)가 타입을 정한다:

| 열거값 | 계약 type | 값 필드 | 값의 출처 |
|---|---|---|---|
| 없음 (기본) | — **미발행** | — | 계약 §16.6: 미장착 = 미발행 |
| 도료 분사압 | `pressure_paint` | `bar` | 규격 v3 의 `value` 환산과 동일: (ma−zero)×scale |
| 유리알 분사압 | `pressure_bead` | `bar` | 〃 |
| 유량 | `flow` | `lpm` | 〃 |

🔴 **"J3→J4 이동" 이 설정 한 칸이 되는 자리다.** 센서를 옮기면 GUI 에서
J3 의 `cloud` 를 없음으로, J4 를 도료 분사압으로 바꾸면 끝 — 타입 이름이
새 채널을 따라간다. 펌웨어·젯슨·Cloud 어느 코드도 안 바뀐다.

숫자는 `tx.float_digits` 를 따르지 않고 **소수 1자리로 고정**한다 — 계약
예시(95.4, 7.2, 3.0, 42.5)의 자릿수이고, Cloud 는 "×10 스케일 사용하지 않는
실수"만 요구한다. (환산 정밀도가 더 필요해지면 계약 쪽과 함께 늘린다.)

### 4.3 I2C → temp_road · light

**종류에서 자동 유도** — 별도 설정 없음 (종류가 이미 물리량을 확정한다):

| i2c 종류 | 계약 type | 값 필드 | 비고 |
|---|---|---|---|
| 적외 온도 (MLX90614, quantity=temp_object) | `temp_road` | `degc` | 대상(노면) 온도 |
| 조도 (BH1750) | `light` | `lux` | |
| 온습도 (AM2320) | `temp_air` + `humidity` | `degc` / `pct` | 🔴 **계약 v1.7.0 신규 타입 2종** (사용자 결정 2026-08-21 — "미발행 대신 계약을 늘린다"). 한 수집에서 두 레코드가 나간다 — 계약의 1타입 1값 관례를 지킨다 (§9 pressure 가 paint/bead 로 갈린 것과 같은 결) |

### 4.4 GNSS → gnss

`gnss.enabled` 가 켜져 있고 **fix 가 유효할 때만** 발행한다(위치가 없는 gnss
레코드는 계약에 없다 — lat_e8/lon_e8 이 필수).

| 계약 필드 | 출처 | 비고 |
|---|---|---|
| `lat_e8` `lon_e8` | mk_gnss 의 1e-8 도 정수 (int64) | 🔴 **표현이 이미 동일하다** — 변환 없음, 손실 없음 (mk_gnss.h) |
| `fix` | GGA fix_quality | |
| `sat` | GGA sats | |
| `hdop_x100` | GGA hdop × 100 (정수 반올림) | mk_gnss 에 hdop 보존 필요 여부는 구현 시 확인 — 없으면 파서에 추가 |
| `cs` | **원 GGA 문장의 NMEA 체크섬 2자리** | mk_gnss 에 보존 필드 추가 (신규) |
| `valve` | §4.5 의 밸브 상태 (0/1) | 계약 §3: 직렬화 시점의 상태 태깅 |

발행 시점: **새 fix 마다 1줄** (RMC/GGA 짝이 갱신될 때). 주기 설정과 무관 —
계약 §3 "세션 중 상시 전송" 의 최소 해석.

### 4.5 디지털 입력 → valve, 그리고 밸브 태깅

신규 설정 `cloud.valve`(열거: 없음/J18/J19/J20, 기본 없음)가 **어느 입력이
밸브인가**를 지정한다. 지정된 채널의 **확정 상태 변화마다** `valve` 레코드
1줄(`state`: 0/1)이 **별도로** 나간다(사용자 확정 2026-08-21 — "벨브 NDJSON도
물론 jetson에는 따로 줘야해"). 지정이 없으면 valve 레코드는 미발행, 태깅은 0.

**밸브 태깅 (사용자 요청 2026-08-21)**: gnss 는 계약 §3 이 `valve` 필드를
필수로 요구하므로 항상 태깅한다. **다른 센서 레코드에도** 채널별 체크박스
(`ain{n}.valve_tag`·i2c 포트별 동등 항목, bool, 기본 꺼짐)를 켜면 그 채널의
클라우드 레코드에 `"valve":0/1` 이 붙는다 — 직렬화 시점의 밸브 상태
(gnss 와 같은 의미). 계약 §15 의 "필드 추가 허용" 범위라 schema_ver 는
그대로 1 이고, v1.7.0 문서에 "선택 필드 valve 를 모든 센서 레코드에 허용"
으로 명시한다.

### 4.6 device_capability (계약 §16)

부팅 후 **설정 로드가 끝난 시점에 1회** 발행:

- `sensors`: 설정에서 유도 — `ain{n}.cloud` ≠ 없음인 타입들 + `i2c1x.cloud`
  켜진 포트의 유도 타입들 + (`gnss.enabled`) `"gnss"` + (`gnss.imu`) `"imu"`.
  중복 제거. `valve` 는 넣지 않는다 (계약 §16.3).
- `fw_version`: `FW_VERSION`(main.c).
- 캐시·재발행은 젯슨의 몫이다(계약 §16.1) — 보드는 부팅 1회만.

설정이 **런타임에 바뀌면**(cloud 관련 항목의 $CFG,SET) 즉시 1회 재발행한다 —
계약 §16.4 의 "변경 도착 시 UPDATE" 를 살리는 최소 방법이다.

### 4.7 발행 시점 — 보드는 수집되는 대로 보낸다

🔴 **[개정 2026-08-30~31, 사용자 결정 — HANDOFF_0831 결정 1·검토 1]**
아래의 "송신 주기를 두지 않는다"와 "수집 주기 = 발행 주기"는 폐기됐다:
i2c 는 포트별 `i2cN.tx_period_ms` 로 캐시 최신값을 반복 송신하고, ain 은
mk_telem 의 골격(tx.period_ms 게이트 + 큐 드레인 + last 반복)을 상속했다.
서버 페이싱·집계가 젯슨/Cloud 몫이라는 원칙 자체는 그대로다.

~~🔴 **클라우드 송신 주기 설정은 두지 않는다** (사용자 확정 2026-08-21 —
"클라우드 송신 주기는 jetson 이 알아서 할 일... 보드는 그냥 잘 수집해서 잘
보내기만 하면 돼"). 채널의 **수집 주기가 곧 발행 주기**다:~~

- ain: `ain{n}.period_ms`(기존 항목) 마다 새 표본 1개 → 클라우드 레코드 1줄
- i2c: 실효 주기(기존 — max(설정 주기, 변환 시간)) 마다 1줄
- gnss: 새 유효 fix 마다 1줄 · valve: 확정 엣지마다 1줄 ·
  capability: 부팅·클라우드 설정 변경 시 1줄
- 클라우드 쪽 페이싱·집계·저장 판정은 전부 젯슨/Cloud 의 몫이다

대역폭 상한 확인: 최악(7채널 × 10 ms, 줄 ~110 B)이면 77 KB/s 로 921600
(92 KB/s)의 84 % — 들어간다. 링이 순간 포화하면 줄 단위로 버리고 센다
(기존 mk_jet 계약 — Cloud 는 dedupe·실시간 위주라 계약이 흡수).

### 4.8 IMU — UM981 에서 (신규, 사용자 확정 2026-08-21)

UM981 의 원시 IMU 출력으로 계약 `imu` 타입(§7)을 발행한다. **확인 완료**
(`docs/datasheet/UM981_Auto_Commands_R1.0.pdf`, 2026-08-21 확보):

1. 출력 로그: **RAWIMUX** (p.20 §2.3.5) — `RAWIMUXA 0.01` 로 최대 100 Hz
   ASCII. 가속도 3축 + 자이로 3축 정수 카운트
2. 환산 (p.21 Table 2-14, IMU type 64): 자이로 × 250/32767 → **dps**,
   가속도 × 2/32767 → **g** — 계약 §7 단위와 일치. 🔴 필드 순서가
   **Z, −Y, X** (외함 좌표계) — 부호·축 재배열을 파서가 한다
3. 🔴 **자기계 없음** — RAWIMUX 에 mx·my·mz 가 없다. **v1.7.0 개정으로
   지자기 3필드를 필수→선택으로 완화**하고 UM981 유래 imu 레코드는 6필드
   (ax~gz)만 싣는다 (sentinel 금지 — 없는 값은 생략)
4. 설정: `gnss.imu`(bool, 기본 꺼짐) — 켜면 UM981 에 `RAWIMUXA` 출력을
   명령하고 수신분을 imu 레코드로 발행. 주기는 모듈 설정(0.1s 권장 = 10 Hz
   — 100 Hz 는 921600 링크와 본선 파서 부담을 먼저 계산한 뒤)

## 7. 계약 개정 — v1.6.0 → v1.7.0

이 설계와 함께 `docs/데이터 스키마 명세서_v1.6.0.md` 를 **v1.7.0 으로
개정**한다 (계약도 이 프로젝트 소유 — 사용자 결정 2026-08-21):

1. 신규 record type 2종: `temp_air`(대기 온도, `degc`) · `humidity`(상대
   습도, `pct` 0~100). 필드명은 계약의 단위 약어 관례(bar·lpm·degc·lux)를
   따른다.
2. §2 type 허용 집합, §12 단위 집계, §16.3 sensors 허용값에 두 타입 추가.
3. **`valve` 를 모든 센서 레코드의 선택 필드로 허용** (§3 의 gnss 필수
   태깅은 그대로) — 사용자 요청: 다른 센서에도 채널별 체크박스로 태깅.
4. **`imu` 의 mx·my·mz 를 필수→선택으로 완화** — UM981 RAWIMUX 에 자기계가
   없다(§4.8 근거). Dead Reckoning 입력으로 가속도·자이로 6필드는 유지.
5. 변경 이력에 v1.7.0 행 추가 — "MarkON Studio(STM32 v2.0) 합류. AM2320
   온습도·밸브 태깅 일반화·UM981 IMU 반영."

🔴 Cloud validator (backend `core/validator.py`) 도 두 타입을 허용해야
저장된다 — 계약 §14 대로 수용 정책은 Cloud 쪽 몫이며, **이 개정을 Cloud
저장소에 반영하는 일은 이 설계의 범위 밖**이다 (사용자가 그쪽 프로젝트에서
진행). 반영 전까지 두 타입은 validator 에서 거절될 수 있다 — 나머지 타입은
그대로 통과한다.

## 8. 비범위 (B단계로 미룸)

- USART2 **수신** 전부: `$TREQ`/`$TRES` 시간동기(→ time_source "host_clock"
  등급 추가), `$HB` 송신, `$SACK` 세션/도색 명령. 지금 안전 시험이 RX 를
  막아 두었다 — B단계 설계에서 푼다.
- carspd — OBD 하드웨어 없음 → 계약 §16.6 대로 미발행 (영구적 비범위).
  (imu 는 §4.8 로 A단계 범위에 **들어왔다** — UM981 RAWIMUX.)
- Cloud 저장소(validator·DB)에 v1.7.0 반영 — 사용자의 별도 작업.

## 9. 위험과 완화

| 위험 | 완화 |
|---|---|
| 젯슨 앱이 기대하는 baud 2M ≠ 링크 921600 | 젯슨에서 `LANEMARK_SERIAL_BAUD=921600` (환경변수, 실측 확인). 품질 개선 뒤 2M 승격은 `MK_JET_BAUD` 한 줄 |
| device_clock 일 때 `t` 가 절대시간이 아님 | 계약이 이미 그 상황을 정의한다 — time_source 로 구분, Cloud validator 가 보정 (§1) |
| J29 링크 유실(best-effort) | Cloud 는 실시간 표시 위주, 정밀 원본은 본선. dedupe 는 (device_id,t,type) — 중복도 계약이 흡수 |
| 계약 문서가 git 밖(docs/) | 이 설계 문서에 참조 버전(v1.6.0)을 박제. 계약이 바뀌면 여기부터 갱신 |
