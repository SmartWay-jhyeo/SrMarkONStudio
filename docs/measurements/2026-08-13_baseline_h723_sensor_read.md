# 기준선 측정 — 참고 펌웨어 `h723_sensor_read`

**측정일:** 2026-08-13
**대상:** STM32 v2.0 실물 보드, USB-C 단독 연결, **센서 미연결**
**경로:** COM23 (BMP → H723 USART3), 115200 baud
**펌웨어:** 보드에 이미 올라가 있던 `h723_sensor_read` (schema_ver 2)
**원본 로그:** scratchpad `baseline.ndjson` (308 KB, 60초)

## 왜 쟀나

계획서와 설계 스펙이 참고 ADS1256 드라이버의 **블로킹 동작**을 근거로 신규
펌웨어를 새로 짜기로 했다. 그 근거가 계산값(한 바퀴 약 117 ms, 장애 시 최악
3.5초)이었고 실측이 없었다. 신규 구현의 before/after 기준도 필요했다.

## 결과

| 항목 | 값 |
|---|---|
| 수신 | 60초 / 정상 2,106줄 / 깨짐 1줄 (0.05%) |
| seq | 15352 ~ 17457, 범위 2106, **누락 0 (0.000%)** |
| 7채널 한 바퀴 | 최소 140 / **중앙 203** / p95 204 / 최대 219 ms |
| 채널당 실효 주기 | 203 ms → 채널 하나가 초당 4.9회 |
| `line` 필드 | 전부 `1` (단선) — 센서 미연결이므로 정확 |
| `code` 범위 | −511 ~ 254 (0 부근 잡음, 음수 포함) |

## 판단

**1. 한 바퀴 203 ms — 계산값 117 ms 보다 나쁘다.**

계산은 DRATE 60 SPS 기준 변환 대기(16.7 ms) × 7채널 ≈ 117 ms 였다. 실측이
203 ms 이므로 채널 전환(MUX→SYNC→WAKEUP)과 GPIO 비트뱅 전송에 계산에 넣지
않은 비용이 더 있다. **참고 드라이버가 메인 루프를 실제로 그만큼 막는다**는
것이 확인됐고, 장애 시 최악 3.5초라는 추정의 신빙성도 올라간다.

설계 스펙 §7.4 의 기능 요구(메인 루프 정지 10 ms 이하)를 **장애가 없어도
20배 위반한다.**

**2. 센서 미연결이 전부 `line:1`(단선)로 나온다.**

4–20 mA 가 0–20 이 아닌 이유가 실물에서 확인됐다. `code` 가 −511~254 로
0 부근을 오가는데, 0–20 mA 규격이었으면 이걸 "0 을 읽었다"로 볼 수밖에 없다.
GUI 의 `read_loop` 가 4 mA 미만을 `루프 단선` 으로 표시하는 설계가 맞다.

**3. 이 경로에서는 유실이 없다.**

60초 2,106줄에 누락 0. 다만 **이것은 USB CDC 경로(BMP 경유)**이고, Q2 가 2%
유실을 겪은 것은 **J29 직결 UART → Jetson** 이다. 다른 링크이므로 이 결과로
그 문제가 없다고 말할 수 없다. J29 경로는 따로 측정해야 한다.

**4. 깨짐 1줄 (0.05%).**

Q2 가 보고한 0.4~1% 손상보다 훨씬 낮다. 역시 링크가 달라 직접 비교는 못 한다.
