# 921600 baud 실기기 확인 (2026-08-14) [실증]

**사용자 확정.** 115200 → 921600 으로 올렸다.

## 왜

`docs/measurements/2026-08-14_link_budget.md` 의 계산에서:

| baud | 텔레메트리 사용률 | 설정 화면 열기 |
|---|---:|---:|
| 115200 | 94.8% | **16.7 초** |
| 921600 | 11.8% | 0.1 초 |

115200 에서는 사용자 요구의 핵심("USB 를 연결했을 때만 GUI 로 설정하고
제어한다")이 기본 설정에서 성립하지 않았다.

## 미확인이었던 것

**BMP 의 USB-VCP 가 이 속도를 통과시키는지** 를 몰라 기본값을 바꾸지
않고 있었다. 이제 확인했다.

## H723 쪽 여유 [계산]

APB1 = 64 MHz (HSI, PLL 없음, 모든 분주 1).

```
USARTDIV = 64,000,000 / 921,600 = 69.444
BRR (OVER16, 정수)               = 69
실제 baud = 64,000,000 / 69      = 927,536
오차 = (927,536 - 921,600) / 921,600 = +0.64%
```

UART 허용 오차(보통 2~3%) 안이다.

## 실기기 결과 [실증]

굽고 나서 COM23 을 921600 으로 열었다.

### 기능 확인 — 전부 통과

115200 에서 통과하던 항목이 그대로 통과한다.

```
$HB 1 Hz, 체크섬 일치
$ID  -> {"schema_ver":3,"seq":0,"t":...,"type":"id",...} + $SACK,ID,OK*13
$STAT -> $SACK,STAT,ERR,UNSUPPORTED*34
깨진 $HB -> 응답 없음 (규격 §3 예외)
깨진 $ID -> $SACK,ID,ERR,CHECKSUM*73
```

### 무결성 확인

하트비트 몇 개가 온다고 링크가 튼튼한 것은 아니다. Q2 에서 2 Mbps 로 2%
유실이 실측됐고 원인이 미해결이므로, 속도를 올리면 그런 문제를 만날 수 있다.
`$ID` 를 빠르게 반복해 응답이 깨지는지 봤다.

```
200회 $ID 왕복, 30.1초
  정상 응답        : 200
  응답 누락        : 0
  JSON 깨짐        : 0
  SACK 체크섬 깨짐 : 0
  그 사이 받은 $HB : 31
```

**깨진 것이 하나도 없다.**

## 어디를 바꿨나

값은 한 곳에만 둔다 — `host/core/limits.py` 의 `DEFAULT_BAUD`.

```
firmware/stage1/main.c        UART_BAUD
host/core/limits.py           DEFAULT_BAUD   ← 호스트 쪽 단일 출처
host/service/board_service.py
host/gui/app.py
tools/cli/markon_cli.py
tools/simulator/serial_server.py
```

`host/tests/test_limits.py` 가 펌웨어 `main.c` 의 `UART_BAUD` 를 읽어
`DEFAULT_BAUD` 와 대조한다. 갈리면 전선에 쓰레기만 흐르고 증상은
"아무것도 안 나온다" 라 원인을 찾기 어렵다.

## 아직 확인 안 한 것

- **Jetson 직결(J29)** 은 BMP 를 거치지 않으므로 별개다 [미확인]
- **ADS1256 이 들어온 뒤의 실제 부하** — 지금은 `$HB` 와 `$ID` 뿐이라
  링크가 거의 비어 있다. 3단계에서 초당 11 kB 가 흐를 때 다시 재야 한다.
